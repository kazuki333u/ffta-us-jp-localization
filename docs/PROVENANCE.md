# データの出所と監査

このリポジトリに**公式ROM由来の生データが含まれていないこと**を、
どう確かめたかの記録です。

法的な判断ではありません。**事故による混入を防ぐための機械的な検査**です。

---

## 1. 検査の実行方法

```
# ROM不要 (CIで毎回実行)
python tools/public_audit.py

# ROMありの完全版 (公開前にローカルで実行)
python tools/public_audit.py --us FFTA_US.gba --jp FFTA_JP.gba
```

---

## 2. 検査項目

| 検査 | 内容 | ROM |
|---|---|---|
| `forbidden-files` | ROM / セーブ / セーブステート / パッチ / アーカイブ / 画像 / バイナリが追跡されていないか | 不要 |
| `local-paths` | 開発機の絶対パス、ユーザー名、メールアドレス、トークン、秘密鍵が残っていないか | 不要 |
| `manifest-schema` | 全マニフェストが解析でき、宣言された件数と実体が一致するか | 不要 |
| `retail-text` | 公式の原文がそのまま保存されていないか | 不要 |
| `decoded-records` | フィールド名によらず、復号済みの公式レコードが混入していないか | 不要 |
| `rom-substring` | 追跡ファイルがROMの長い連続バイト列を再現していないか | **必要** |
| `provenance` | 上流由来ファイルが宣言され、帰属表示されているか | 不要 |
| `chain-integrity` | ビルダーが import する全モジュールが存在し、構文が通るか | 不要 |
| `required-files` | 公開に必要な文書が揃っているか | 不要 |

CI (GitHub Actions) はROM不要の項目のみを実行します。
**CIのsecret / cache / artifact にROMを置く設計にはしていません。**
CIからROMをダウンロードする処理もありません。

## 3. 公式テキストの扱い

### JP版の文章・フォント・グラフィック

**このリポジトリには一切含まれていません。**

すべてビルド時に、ユーザー自身のJP版ROMから取り出されます。
リポジトリが持っているのは「JP版のレコード N を US版のレコード M へ」
という**数値の対応表**だけです。

### US版の英語原文

翻訳マニフェストは、整合性チェックのために
「このレコードは当時この英語だった」という記録を必要とします。

公開版ではこれを **SHA-256 ダイジェストに置き換えています**。

- 置き換えたフィールド数: **1,571**
- 残した文字列: **2 件のみ**
  - `words:ico/8` = `/`
  - `words:ico/9` = 記号の並び

  この2件は自然言語を含まず、ビルドがその値を**そのまま書き戻す**
  必要があるため、ダイジェストでは代用できません。

チェックの強度は変わっていません (SHA-256 の完全一致)。
仕組みは [`ARCHITECTURE.md`](ARCHITECTURE.md) §3 を参照してください。

`retail-text` 検査が、この2件以外の原文フィールドを常時拒否します。

さらに `decoded-records` 検査が、**フィールド名によらず**「公式テキストを
復号した形」を検出します。判定は「markup が語の区切りとして使われているか」
です — 符号化されたレコードでは `The{52}palace{52}and{4D}the` のように
制御コードが英単語の間に空白なしで入りますが、本プロジェクトが書いた注記は
`{5117}ウォッチ` のように日本語の隣に置くか `[5117] ポイント` のように
空白を伴うため、区別できます。

この2つの検査は補完関係にあります。`retail-text` は既知のフィールド名を、
`decoded-records` は**未知のフィールド名**を担当します。実際、後者は
開発リポジトリの生成レポートに含まれる 20 件の復号済みレコードを検出します
(そのファイルは §6 のとおり公開ツリーへ持ち込んでいません)。

## 4. ROM連続バイト列の検査

`rom-substring` 検査は、両方のROMから **32バイトの窓**をすべて取り出し、
追跡ファイルのあらゆる32バイト窓と照合します。

**なぜ32バイトか**

- テキストファイルが偶然32バイト一致することは、実質的にありません。
- 一方で、貼り付けられたテーブル、フォントシート、テキストダンプは
  必ず32バイトを超える連続一致を持ちます。

短すぎる窓 (4〜8バイト) は、ASCII文字列や `00` の並びで
誤検出が大量に出ます。32バイトはその境界の十分外側です。

**結果 (Public Beta 3 / RC24):** 両ROMから取り出した
**11,067,562 個の相異なる32バイト窓**に対し、追跡ファイル 91 件を走査して
**一致は 0 件**でした。

なお、ビルドチェーンのソースには、ジョブ名 (44件) や
アイテムの分類名 (29件) のような**短い識別子の表**が含まれます。
これらはレコードの並び順・件数を検証するためのラベルであり、
ROMのバイト列を複製したものではありません
(いずれも上記の32バイト窓検査を通過しています)。

## 6. 開発リポジトリからの導出

このリポジトリは開発リポジトリのミラーではなく、
`tools/sync_from_canonical.py` による**機械的な部分集合**です。

```
python tools/sync_from_canonical.py --canonical <開発リポジトリのパス>
python tools/sync_from_canonical.py --canonical <パス> --check   # 差分確認のみ
```

導出時に行われること:

1. 最終ビルダーから **import グラフを辿って到達するモジュールだけ**を抽出
   (開発リポジトリの Python ファイルのうち、実際に使われる分のみ)
2. 英語原文フィールドを **SHA-256 ダイジェストへ置換**
3. 整合性チェックの比較対象を、マニフェストの文字列から
   **ユーザーのROMから読んだ値のダイジェスト**へ書き換え
4. 探索的解析ツール、実行時QAハーネス、証跡ダンプ、セーブステート、
   スクリーンショット、生成ROM、生成パッチは**一切持ち込まない**
5. **Git履歴を持ち込まない** — このリポジトリは新規に初期化されています

何がどう導出されたかは `src/localizer/chain/SYNC_MANIFEST.json` に
機械可読な形で記録されています。

### 持ち込まなかったもの

| 種類 | 理由 |
|---|---|
| 実行時QAハーネス | エミュレータとセーブステートに依存し、ローカルパスを含む |
| セーブステート / セーブデータ | プレイヤー入力名を含む可能性がある |
| 証跡ダンプ / メモリダンプ / トレース | ROM由来データを含む |
| スクリーンショット | ROM由来のグラフィックそのもの |
| 生成ROM / BPSパッチ | 生成物であり、リポジトリに置くべきものではない |
| 探索的解析スクリプト | ビルドに不要 |
| 過去の誤った仮説を含む文書 | 公開価値がない |
| 生成された監査レポート | ビルドが読まないただの出力で、公式テキストを復号した状態で含む |
| Git履歴 | 上記すべてを含みうる |

## 7. 配布形態について

現時点では **2本のROMからローカルでビルドする方式のみ**を提供します。

BPS等の差分パッチは、開発側では生成できますが、
**このリポジトリには含めません。**

「差分パッチだから安全」と自動的に言えるわけではないため、
公開するかどうかは別途あらためて判断します。
